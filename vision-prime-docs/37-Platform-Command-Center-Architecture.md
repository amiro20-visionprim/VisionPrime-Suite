# 37 — اتاق فرماندهی پلتفرم (Super Admin / Command Center) — تحلیل معماری عمیق

> **وضعیت:** پیشنهادی — مبنای فازبندی اتمی بعدی (پیش از شروع کد)
> **تاریخ:** 2026-08-17
> **مرتبط با:** D-013 (اتوماسیون سرتاسری)، D-020 (قانون مستندمحوری)، D-021 (برند)، سند ۰۶ (RBAC)، سند ۰۹ (ERD)، سند ۳۵ (بازطراحی UX)
> **سؤال مالک:** «پنل سوپرادمین من برای مدیریت و رصد کل اکوسیستم کجاست؟ اتاق فرماندهی و مانیتور من کجاست؟»

## ۱) چکیدهٔ اجرایی

پاسخ صادقانه به سؤال مالک: **پنل سوپرادمین امروز وجود ندارد.** آنچه هست فقط یک ردیف نقش `super-admin` در جدول نقشها + یک بلوک `roleMeta` در داشبورد آژانس است که همان ۳ لینک داخل **سازمان جاری** را نشان میدهد. هیچ لایهٔ «پلتفرم» (بالای سازمانها) وجود ندارد: نه مدیریت بینسازمانی، نه اشتراک/پرداخت، نه رصد سراسری کلیدهای AI، نه مانیتورینگ فنی، نه view مالی.

این سند با نگاه مهندس معماری SaaS + استراتژیست محصول + مدیر محصول، کل این لایه را از ۱۰ زاویه واکاوی میکند، نقاط کور را فهرست میکند و نقشهٔ راه فازبندیشده میدهد تا «کوچکترین نقطهٔ کور فکرنشده» باقی نماند.

## ۲) معماری فعلی — ممیزی صادقانه (وضعیت موجود)

### ۲-۱ هویت و دسترسی
| مورد | وضعیت |
|---|---|
| جدول `roles` با نقش `super-admin` | ✅ وجود دارد (seeder: `superadmin@visionprime.test`) |

### ۲-۴ معماری چندمستأجری
- تنها مکانیزم جداسازی: ستون `organization_id` + سرویس `CurrentOrganization` (یک org در هر request).
- هیچ لایهٔ «بدون سازمان / بالای سازمان» وجود ندارد — سوپرادمین همیشه یک org جاری دارد.
- کاربران چند-سازمانی (یک کاربر در چند org) پشتیبانی میشود در `memberships`، ولی **سوییچر org در UI وجود ندارد**.

## ۳) تحلیل ده‌زاویه‌ای

### زاویه ۱ — محصول و استراتژی بیزینس

**موقعیت در اکوسیستم:** SUITE یک SaaS سه‌لایه است:
```
پلتفرم (مالک: ویژن‌پرایم)  ← پنل سوپرادمین (مفقود!)
   └─ سازمان/آژانس (مستأجر)
        ├─ اعضا و نقش‌ها
        ├─ مشتریان (کلاینت‌ها)
        │    └─ پروژه‌ها → سایت‌ها → GSC/وردپرس/اتوماسیون/AI
        └─ اشتراک و پرداخت (مفقود!)
```

**نکات استراتژیک:**
1. **مدل درآمد باید از همین حالا شکل بگیرد** — حتی اگر در MVP پرداخت واقعی نباشد، ستون‌ها باید موجود باشند تا بعداً بدون migration مهاجرت سنگین، فعال شوند.
2. **قیمت‌گذاری باید به «ظرفیت» گره بخورد نه «کاربر»**: پلن‌ها بر اساس تعداد سایت/کلاینت/توکن AI/پروفایل اتوماسیون. (D-010 لندینگ‌ها Tier 1/2/3 دارد — پلن‌ها می‌توانند همین Tierها را منعکس کنند.)
3. **واحد ارزش = سایت فعالِ متصل** — درآمد باید حول همین متریک گزارش شود.
4. **توسعهٔ محصول باید دید پلتفرم داشته باشد**: هر فیچر آینده باید قابل شمارش per-org باشد (usage metering) تا پلن‌بندی واقعی شود.

### زاویه ۲ — مدل داده (ERD پیشنهادی)

جدول‌های جدید (همه با `organization_id` در صورت نیاز + soft deletes):

```text
plans
  id, key (slug), name, description
  price_monthly (decimal), price_yearly (decimal), currency (IRR/IRT)
  limits (json): max_sites, max_clients, max_ai_tokens_monthly, max_profiles
  features (json): feature_flags[]
  is_active, sort, timestamps, softDeletes

subscriptions
  id, organization_id (FK, unique active), plan_id (FK)
  status: trialing | active | past_due | canceled | suspended
  trial_ends_at, starts_at, current_period_end
  auto_renew (bool), cancel_at_period_end (bool)
  timestamps, softDeletes

payments
  id, organization_id, subscription_id (nullable FK)
  amount (decimal), currency, method (zarinpal/idpay/manual/bank)
  status: pending | paid | failed | refunded
  reference (string), gateway_transaction_id, paid_at
  timestamps

invoices
  id, organization_id, subscription_id, payment_id (nullable)
  number (unique), amount, tax, total, status, issued_at
  timestamps

platform_metrics (rollup روزانه برای داشبورد سریع)
  date, orgs_active, orgs_trialing, clients_total, sites_total,
  sites_connected, tokens_in, tokens_out, ai_cost, commands_executed,
  commands_rolled_back, reviews_pending
  unique(date)

platform_events / alarm (اختیاری، جایگزین polling)
  type: subscription.expiring | payment.failed | ai.cost_spike |
       site.disconnected | job.failure | org.suspended
  severity, payload (json), seen_at, resolved_at
```

**نکتهٔ معماری مهم:** جداول متریک را **rollup روزانه** نگه داریم (`platform_metrics`) نه COUNT سنگین هر بار روی `audit_logs`/`ai_generations` — داشبورد پلتفرم باید حتی با ۱۰ هزار سازمان سریع بماند.

### زاویه ۳ — امنیت (بالاترین اولویت)

تهدیدها و کنترل‌های پیشنهادی:

| تهدید | کنترل |
|---|---|
| دسترسی غیرمجاز به پنل پلتفرم | middleware `platform.only` + نقش super-admin + **MFA اجباری** + rate-limit سختگیرانه |
| نشت دادهٔ بین‌سازمانی از کوئری پلتفرم | **همهٔ کوئری‌های پلتفرم به‌صورت صریح و ممیزی‌شده**؛ تست نفوذ داده (org A هرگز org B را نمی‌بیند) |
| نمایش کلید AI در UI | کلیدها **هرگز** بازگردانده نمی‌شوند؛ فقط `has_key` + masked آخرین ۴ کاراکتر |
| سوءاستفاده از impersonation | فقط super-admin، با لاگ کامل (چه کسی، چه زمانی، به‌جای چه کسی، چه کرد)، بنر قرمز در session |
| تغییر مخرب (حذف org، تعلیق) | **همهٔ اکشن‌های پلتفرم در `audit_logs`** با actor + before/after + دلیل الزامی |
| کلید API در git/env | کلیدها فقط در `ai_provider_settings` رمزنگاری‌شده؛ هیچ‌جا hard-code نمی‌شود |
| حملهٔ CSRF روی اکشن‌های حساس | همهٔ اکشن‌های پلتفرم POST با CSRF + تأیید دوم (confirm modal با تایپ «حذف») |

### زاویه ۴ — مالی و صورتحساب (واقعیت ایران)

- **درگاه‌ها:** زارین‌پال / IDPay / Pay.ir / انتقال بانکی. معماری `PaymentGateway` abstraction با درایورها (در MVP: درایور `manual` + stub برای تست).
- **واحد پول:** ریال/تومان + امکان نمایش مبلغ به‌صورت شمسی.
- **dunning:** پرداخت ناموفق → وضعیت `past_due` → اعلان → (اختیاری) تعلیق در روز X.
- **تست و idempotency:** webhook درگاه باید idempotent باشد (کلید reference یکتا).
- **فاکتور:** فاکتور ساده با شمارهٔ یکتا + مالیات (در ایران در نسخهٔ بعدی با سامانهٔ مودیان).

### زاویه ۵ — عملیات و رصد فنی

ویجت‌های مانیتورینگ پلتفرم:
1. **سلامت صف:** تعداد jobهای pending/failed (جدول `jobs`/`failed_jobs`).
2. **وضعیت scheduler:** آخرین اجرای موفق هر job زمان‌بندی‌شده (gsc:import، LearningLoop، RollbackMonitor، ReleaseScheduledCommands، RemindScheduledPublishes، ProcessQueuedCommands) — از `audit_logs` یا جدول run-log.
3. **مصرف AI سراسری:** مجموع توکن‌ها/هزینهٔ هر سازمان این ماه؛ هشدار spike.
4. **اتصال‌های ضعیف:** سایت‌هایی که heartbeat وردپرس ندارند / توکن GSC نزدیک انقضا.
5. **Emergency Stop سراسری:** دکمهٔ توقف اضطراری **کل پلتفرم** (بالای EmergencyStop فعلی که per-site است).

### زاویه ۶ — UX اتاق فرماندهی (استاندارد فاز A–D)

- لایوت جداگانهٔ `PlatformLayout` (شبیه AppLayout ولی آیکون متفاوت + بنر «پلتفرم»).
- **داشبورد فرماندهی:** KPI کارت‌های متحرک (سازمان‌های فعال/درحال trial، مشتریان، سایت‌های متصل، درآمد ماه، توکن‌های AI، صف‌های خطا) + چارت رشد (VAreaChart/VBarChart موجود) + آخرین رویدادها.
- **Drill-down یکپارچه:** پلتفرم → سازمان → مشتری → سایت → جزئیات (deep-link به همان صفحات موجود).
- **جستجوی سراسری** (Command Palette): پیدا کردن سازمان/مشتری/سایت با چند کلید — حیاتی وقتی ده‌ها سازمان داریم.
- **همهٔ جداول** با فیلتر/مرتب‌سازی/صفحه‌بندی + Export CSV.
- زبان: برای مالک، **فنی ولی روون** — هر عدد با hint (💡) که یعنی چه.

### زاویه ۷ — مقیاس و عملکرد

- rollup روزانه (`platform_metrics`) + کش صفحهٔ داشبورد (مثلاً ۵ دقیقه).
- کوئری‌های لیست سازمان‌ها با pagination و index روی `status`, `created_at`.
- اکشن‌های سنگین (export، ارسال اعلان گروهی) → queue.

### زاویه ۸ — محلی‌سازی و قانون

- تقویم شمسی (زیرساخت `locale` موجود)، ارز IRR/IRT، فرمت اعداد فارسی.
- فاکتور رسمی و سامانهٔ مودیان: **در scope فعلی نه** — فقط ساختار فاکتور ساده.
- حریم خصوصی: حذف org باید soft-delete + بایگانی باشد (بازیابی‌پذیر).

### زاویه ۹ — ریسک‌ها و نقاط کور (پاسخ مستقیم به خواستهٔ مالک)

1. **نبود لایهٔ پلتفرم در معماری** — سوپرادمین امروز «عضو org» است؛ باید از org مستقل شود.
2. **نبود دادهٔ مالی** — بدون plans/subscriptions/payments نمی‌توانیم حتی «مدیریت مشتری از پرداختی تا جزئیات اشتراک» را شروع کنیم.
3. **نشت داده** — هر کوئری پلتفرم باید به‌صورت صریح scope شود؛ آزمایش isolation الزامی است.
4. **نمایش کلیدهای AI** — امنیت: هرگز کلید کامل نمایش داده نشود؛ رصد فقط status/مصرف.
5. **impersonation بدون audit** — خطرناک‌ترین قابلیت؛ بدون لاگ کامل فعال نمی‌شود.
6. **Emergency Stop سراسری** — اتوماسیون می‌تواند در ده‌ها سایت هم‌زمان عمل کند؛ پلتفرم باید یک دکمهٔ توقف کلی داشته باشد.
7. **هزینهٔ AI خارج از کنترل** — سقف مصرف ماهانه per-org + هشدار.
8. **بکاپ DB** — git فقط کد را حفظ می‌کند؛ نیاز به dump دوره‌ای DB (حتی sqlite) داریم.
9. **صفحه‌های پلتفرم بدون رصد وضعیت** — بدون مانیتورینگ صف/scheduler، «اتاق فرماندهی» واقعی نیست.
10. **سوییچر org** — برای کاربران چند-سازمانی لازم است (کاربر مالکِ چند org).

### زاویه ۱۰ — مرزها و تصمیم‌های باز (برای مالک)

| تصمیم | پیشنهاد من |
|---|---|
| مسیر پلتفرم: `/platform/*` جدا یا داخل `/app`؟ | **`/platform/*` جدا** با `PlatformLayout` و middleware مخصوص — تمیز و قابل تست |
| آیا super-admin عضو org هم می‌ماند؟ | بله ولی دسترسی‌های org جدا از دسترسی‌های پلتفرم |
| پرداخت واقعی در همین فاز؟ | **خیر** — ساختار داده + درگاه manual/stub؛ درگاه واقعی فاز بعدی |
| impersonation در این فاز؟ | بله با audit کامل + بنر — ارزش پشتیبانی بالاست |
| مانیتورینگ صف در این فاز؟ | بله حداقل read-only |
| بکاپ خودکار DB در این فاز؟ | بله یک command ساده + برنامهٔ زمان‌بندی |

## ۴) نقشهٔ راه فازبندی (پیشنهادی — بدون تسک اتمی)

- **E0 — زیرساخت دادهٔ مالی:** plans + subscriptions + payments + invoices + platform_metrics + migration + seeder نمونه.
- **E1 — هستهٔ پلتفرم:** PlatformLayout + middleware `platform.only` + مسیر `/platform/*` + Dashboard فرماندهی (KPI + چارت + رویدادها).
- **E2 — مدیریت سازمان‌ها:** لیست + جزئیات (اعضا/کلاینت‌ها/سایت‌ها/کلیدهای AI/مصرف) + تعلیق/فعال‌سازی + impersonation با audit.
- **E3 — مشتریان و اشتراک‌ها:** مدیریت پلن هر org، ثبت پرداخت دستی، تمدید، تغییر پلن، dunning ساده.
- **E4 — رصد فنی:** سلامت صف/scheduler، مصرف AI سراسری + سقف، وضعیت اتصال‌ها، Emergency Stop سراسری.
- **E5 — گزارش و بکاپ:** گزارش درآمد/رشد/سلامت، Export CSV، بکاپ DB + سوییچر org.

**اولویت من:** E0 → E1 → E2 → E4 (رصد) → E3 (مالی عملیاتی) → E5.
دلیل: اول «دیده‌شدن» (E1+E2+E4) و «داده» (E0)، بعد «عمل مالی» (E3) — چون بدون دیده‌شدن، مدیریت مالی کور است.

## ۵) معیارهای پذیرش (Definition of Done هر فاز)

- هر جدول جدید migration + index مناسب + soft delete دارد.
- هر مسیر `/platform/*` با middleware + تست دسترسی (غیر super-admin → 403) پوشش دارد.
- **تست ایزوله‌سازی داده:** org A نمی‌تواند دادهٔ org B را در هیچ API پلتفرم ببیند.
- همهٔ اکشن‌های پلتفرم در `audit_logs` با actor ثبت می‌شوند.
- هیچ کلید API به‌صورت کامل در response قرار نمی‌گیرد.
- typecheck ✓ lint ✓ build ✓ pint ✓ تست‌های PHP سبز ✓
- مستندات مرتبط (۳۷، ۳۵، ۳۱، ۰۴، ۰۹، ۰۶) همگام (D-020).

## ۶) جمع‌بندی

پنل سوپرادمین یک «فیچر» نیست؛ **یک لایهٔ معماری** است که محصول را از «دموی تک‌سازمانی» به «SaaS واقعی چندمستأجری» ارتقا می‌دهد. بدون آن، مالک هیچ اتاق فرماندهی‌ای برای رصد اکوسیستم (مشتریان، سایت‌ها، کلیدهای AI، اشتراک‌ها، پرداخت‌ها، سلامت فنی) ندارد. این سند مسیر را با تمام جزئیات و ریسک‌ها مشخص می‌کند و پس از تأیید مالک، به فازبندی اتمی (سند ۳۸) تبدیل می‌شود.
